> 这篇文章整理自《Harness Engineer：AI Agent 时代的工程范式革命》，聚焦其中最可复用的工程判断。

## 从写 Prompt 到设计运行环境

AI 工程正在经历三个嵌套的阶段：Prompt Engineering 关注如何表达指令；Context Engineering 关注如何把正确的信息放进上下文；Harness Engineering 则把工程对象扩展到 Agent 周围的完整运行环境。

如果 Prompt 是一封信，Context 是信件与附件，那么 Harness 更像整套邮政系统：路线如何选择、什么不能寄、投递失败如何重试，以及人类如何知道包裹走到了哪里。

三者不是替代关系。好的 Harness 仍然需要清晰的 Prompt 和准确的 Context，只是它还要解决长期运行、工具副作用与结果验证的问题。

这次范式变化最重要的地方，是工程师不再只优化一次回答，而是开始优化一个会连续观察、决策、调用工具和修正错误的系统。一次回答的质量可以靠人工检查，运行数小时甚至数天的 Agent 则需要制度化的边界和反馈。

Prompt Engineering 解决“怎么说”，Context Engineering 解决“让模型知道什么”，Harness Engineering 解决“怎样让它长期把事情做完”。

## Agent = Model + Harness

模型提供推理、生成和规划能力，但原始智能并不等于可靠生产力。Harness 决定 Agent 可以使用什么工具、接受什么约束、如何验证结果、怎样从失败中恢复，以及什么时候需要人类介入。

因此，同一个模型放在不同 Harness 中，可能表现得像两个完全不同的系统。模型决定潜在上限，Harness 决定有多少能力能够稳定兑现。

这也提供了一个解释：为什么 Benchmark 上更强的模型，在真实工作流里不一定更好用。Benchmark 通常衡量一次任务中的推理能力，生产环境还会受到工具描述、上下文组织、测试覆盖、重试策略、权限摩擦和状态恢复的影响。任何一环不稳定，都可能吞掉模型升级带来的收益。

更现实的竞争不只是“换一个更强模型”，而是让系统具备模型可替换性。Harness 如果把工具、状态和评估都绑定在某个模型的特殊习惯上，模型升级会变成昂贵迁移；相反，清晰的能力接口与验证标准能让不同模型在同一运行环境中被比较和替换。

## 一个生产级 Harness 的五层结构

### 1. 工具编排

工具层定义 Agent 能调用什么、参数是什么、结果如何返回，以及哪些调用带有副作用。线性管道适合固定流程，动态路由适合开放任务；后者越自由，对权限和监控的要求越高。

工具描述也不是越多越好。比起把全部知识塞进一个超长配置文件，更有效的方式是保留一个短索引，让 Agent 按任务逐层找到相关文档和工具。

工具编排还要处理三个容易被忽视的问题。

第一是**副作用等级**。读取文件、修改文件、发送消息和删除数据库的风险完全不同，不适合共享同一种默认权限。第二是**幂等性**：Agent 重试时，重复读取通常没事，重复付款或重复发信却可能造成事故。第三是**失败语义**：工具需要告诉 Agent 失败是否可重试、是否已经部分执行，以及需要什么补救动作。

因此，工具接口既面向代码，也面向模型。函数能被调用不代表它适合被 Agent 使用；只有行为边界、错误信息和副作用都表达清楚，工具才真正进入 Harness。

### 2. 护栏与约束

生产环境中的自主性，往往不是靠扩大解空间得到的，而是靠缩小解空间获得的。文件边界、依赖方向、危险命令、提交格式和测试要求，都会让 Agent 的行动更可预测。

一种值得保留的方法叫“失败即信号”：Agent 犯错后，不只是人工改掉这一次输出，而是追问 Harness 缺了哪条约束、哪种验证或哪段上下文。修复对象从结果转向生产结果的系统。

约束也存在层级。最外层是不可突破的安全边界，例如禁止访问凭据或执行破坏性命令；中间层是架构规则，例如模块依赖方向、目录责任和接口契约；最内层才是风格偏好，例如命名和格式。

如果所有规则都写成同样强度，Agent 会把真正重要的边界淹没在大量细节中。好的 Harness 会区分“绝对禁止”“需要审批”“建议遵循”和“可以自行判断”，让 Agent 知道自由度究竟在哪里。

自主性也不适合一次性开放。新的 Agent 可以从窄任务、只读权限和强验证开始；当它在某类任务上的成功率与可恢复性被证明后，再逐渐扩大权限。这里积累的不是对模型品牌的信任，而是对具体任务—工具—验证组合的信任。

### 3. 反馈回路

最基础的反馈回路是“写—测—修”：Agent 产生修改，Harness 自动执行测试，把错误日志反馈给 Agent，再进入下一轮修正。

更成熟的系统会把反馈分层：格式检查、单元测试、集成测试、端到端验证与人工审批逐级发生。每一层都把模糊的“做得不好”转化为可行动的信号。

跨 Session 的交接也是反馈回路的一部分。一个进度文件记录做过什么、卡在哪里、下一步是什么，让新的上下文能够继续工作，而不是每次从零开始理解项目。

### 反馈质量比反馈数量更重要

把一整屏构建日志原样丢给模型，并不一定形成有效反馈。真正有用的信号需要回答：失败发生在哪一层、最可能的原因是什么、哪些文件与这次失败相关、下一次尝试是否会产生额外副作用。

反馈延迟也会影响 Agent。修改一个小函数后等待半小时才得到完整集成测试结果，会让它在错误方向上继续扩张。更短的局部测试、更快的静态检查和按影响范围选择验证，可以明显缩短“行动—知道结果”的距离。

最大重试次数同样重要。没有退出条件的 Agent 可能在两个错误方案之间循环，消耗大量时间和 token。Harness 需要识别“继续尝试仍可能成功”和“已经缺少新的信息”之间的差别，在后者发生时主动请求人工判断。

### 4. 可观测性

当 Agent 可以连续行动，人类需要看到的不只是最终答案，还包括动作轨迹、工具参数、耗时、成本、失败重试和异常循环。

可观测性的目标不是复刻模型全部思考，而是让工程师能回答几个现实问题：它做了什么？在哪一步偏离？为什么反复失败？哪些任务的成本正在失控？

一个可用的 Agent 观测体系至少包含四类数据：

1. **动作轨迹**：调用了什么工具、传入什么参数、返回什么状态；
2. **质量结果**：测试通过率、回滚率、人工驳回原因和线上缺陷；
3. **效率数据**：时长、token、重试次数、工具等待时间；
4. **安全事件**：越权尝试、敏感数据访问、异常网络请求和审批绕过。

单看成本也容易误判。一个 Agent 使用更多 token，但减少了返工和人工复核，整体可能更便宜；反过来，单次调用很便宜，却不断制造低质量修改，总成本反而更高。真正有价值的指标应尽量靠近任务结果，而不是停留在模型调用量。

### 5. 配置与状态管理

Agent 需要知道项目规则、当前阶段、历史决策和未完成事项。配置文件负责显式规则，状态文件与版本历史负责时间连续性。

真正有效的配置更像地图，而不是百科全书：顶层只放方向和索引，细节按需加载。信息组织方式，往往比信息总量更重要。

状态管理则解决“时间”问题。长任务会跨越多个上下文窗口，新 Session 如果只读取聊天摘要，很容易重复已经完成的工作，或者忘记此前被否决的方案。更可靠的方法是把任务状态落在可验证的外部载体上：版本历史说明发生了什么，测试说明当前是否正确，进度文件说明下一步意图，任务清单说明还有什么未完成。

初始化 Agent 与执行 Agent 也可以分工。前者建立目录、规则、评估和进度结构；后者在每个 Session 中读取这些状态，只做增量推进。这比让每一轮 Agent 都重新发明工作方式更稳定。

## 多 Agent 并不自动等于更高产

当一个任务被拆给多个 Agent，Harness 还需要处理所有权、依赖和合并问题。如果两个 Agent 同时修改同一文件，或者一个 Agent 依赖另一个尚未验证的结果，并行反而会放大混乱。

适合并行的任务通常边界清楚、输出可独立验证，例如一个 Agent 调研接口，一个 Agent 编写测试，一个 Agent 检查安全风险。强依赖的实现步骤更适合串行推进，或者由协调者明确输入输出契约。

多 Agent 系统中，最稀缺的不是 Agent 数量，而是高质量的任务切分与合并机制。协调层本身就是 Harness 的一部分。

## Harness Engineer 的工作不是“替 Agent 写代码”

这个角色的核心工作，是设计一个能让 Agent 持续产出正确结果的环境：

- 把隐性的项目知识转成机器可读规则；
- 为危险操作设计权限与审批边界；
- 把测试、日志和业务反馈接回 Agent；
- 观察失败模式，并让系统在每次失败后变得更强；
- 判断哪些步骤适合自动化，哪些决策仍值得由人承担。

这和传统工程师的差别不在于是否懂代码，而在于工作重心从“直接生产结果”移到了“设计结果的生产系统”。

### 与相邻角色的边界

Prompt Engineer 更关注单次交互的指令设计；ML Engineer 更关注模型训练、推理和数据管道；平台工程师更关注基础设施的稳定与效率。Harness Engineer 横跨这些边界，但核心对象始终是 Agent 的可靠行动。

这个角色需要同时理解软件架构、评估、安全、可观测性和人机协作。它不一定会成为所有公司的正式职位名称，却很可能成为每个构建 Agent 产品的团队都要承担的一组职责。

## 一个具体例子：从“帮我修 Bug”到可靠工作流

没有 Harness 的 Agent 可能直接搜索代码、猜测原因、修改文件，然后告诉用户“已经修复”。一个更完整的工作流会是：

1. 读取问题描述与仓库规则，确认允许修改的范围；
2. 复现问题，并保存失败证据；
3. 定位相关模块，提出最小改动方案；
4. 修改后运行针对性测试，再运行受影响范围的回归测试；
5. 检查 diff 是否包含无关修改或敏感信息；
6. 如果涉及数据库、权限或外部发布，暂停并等待审批；
7. 记录根因、验证结果与仍未覆盖的风险。

真正带来可靠性的不是某一句 Prompt，而是每一步都有状态、有退出条件、有可验证结果。

## 最大风险：Harness 也会腐化

Context 会随长度增长而退化，跨 Session 会丢失信息，规则会随着项目演进变得过时，Agent 也可能逐渐学会绕开原本有效的约束。

所以 Harness 不是一次性脚手架，而是一套需要持续维护的产品。它需要版本、评估集、回归测试和清理机制；否则早期积累的规则最终会变成新的噪声。

常见的腐化有几种：文档与代码已经不一致，Agent 仍按旧规则工作；为了修复一次偶发错误不断添加局部指令，最终形成互相冲突的规则堆；测试只覆盖已知路径，Agent 学会通过测试却没有真正满足业务目标；进度文件越写越长，新 Session 读取后反而抓不住重点。

这意味着 Harness 也需要自己的“垃圾回收”：删除失效规则、合并重复约束、把频繁出现的人工反馈升级为自动测试，并定期用一组稳定任务比较不同版本的成功率。

## 从项目经验到组织资产

当团队反复解决同一类 Agent 失败，最有价值的产物不是单次修复，而是可复用的 Harness 组件：权限模板、工具契约、评估集、任务交接格式、异常检测规则和人工审批模式。

这些组件会逐渐沉淀成组织的 Agent 操作系统。它们包含的不只是工程规范，也包含业务对“什么叫正确”的定义。模型可以从外部购买，组织对质量、风险和流程的判断却很难复制。

## 下一代工程能力，是把不确定性包进可验证系统

Harness Engineering 并不承诺消灭模型的不确定性。它做的是把不确定性放进一个能观察、能限制、能反馈、能恢复的系统中。

当模型越来越接近基础设施，工程差异就会向模型之外迁移。谁能设计更短的反馈回路、更清晰的边界和更可持续的状态系统，谁就更可能把相同的模型能力转化为真正可用的生产力。

这也是 Harness Engineering 最值得关注的地方：它把讨论从“Agent 会不会替代工程师”，拉回到一个更具体的问题——工程师怎样设计环境，让不确定的智能稳定参与确定的生产过程。
